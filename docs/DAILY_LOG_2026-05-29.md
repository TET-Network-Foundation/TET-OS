## Key Achievements

### 1. 一晩の network 挙動 — resilience の実証

- VPS auto-mine が寝ている間に **11,000+ blocks** 生成。
- Mac node が一度 disconnect (`TimedOut`) → **自動 re-connect** → **441 block の遅れを 約2秒で catch up**。
- 手動介入ゼロ。「落ちても勝手に追いつく」という、production に出して恥ずかしくない挙動を確認できた。前日に直した multi-swarm fix がここで効いている。

### 2. X 反応 / Manu DM の判断

- 前日投稿への反応を確認: **libp2p official + Manu Sheel** から likes 継続。
- Manu への DM は **Phase 0 ship のタイミングまで温存**と判断。今コンタクトするより、動く testnet + faucet + UI が揃ってから出した方が一撃が重い。

### 3. Founder wallet (...0098) lock の調査 (Cursor)

「founder lock を解除して早く世に出したい」という衝動があったが、まず事実を取りに行った。

- **結論: bug ではない**。WP §17.3 に沿った **意図的な 365 日クリフ**設計。
- `locked_balance = 2.5B`、`spendable = 0`。`balance - locked = 0` なので transfer は署名が通っても `InsufficientFunds` で reject される。
- ロック実装は genesis 時に `META_FOUNDER_GENESIS_UNLOCK_AT_MS`（= genesis + 365日）と `META_FOUNDER_GENESIS_LOCKED_MICRO`（= 配分全額 2.5B）を焼き込む方式。
- 解除方法は **時間経過のみ**。途中解除する API / governance はコードに存在しない。`TET_FOUNDER_CLIFF_MS` は genesis 時にしか読まれないため、既存 DB では後から変えられない。
- WP §17.3 では **"cliff vs linear vest" は open（未確定）**。実装の挙動は「1 年クリフで 2.5B を一括 unlock」。

### 4. 戦略 C の確定

検討した選択肢:

- **A**: 今動いている chain をそのまま mainnet にする。
- **B**: 純粋に reset して作り直す。
- **C**: Phase 0 は testnet として実験に使い、Phase 1 で新しい genesis を切る。

決め手は founder lock 調査で判明した事実だった。今の chain には既に **「1 年後に 2.5B が一括 unlock される」クリフが焼き込まれている**。これは AI に評価させると最大級の警告（供給ショック / 中央集権懸念）が出る典型パターンで、**この genesis をそのまま mainnet にする A は不可**。必然的に **C** になる。

- Phase 0 testnet: 既存 chain で faucet / UI / network を実地検証。
- Phase 1 mainnet: 新 genesis で、**cliff + linear** の on-chain vesting lock を最初から正しく設計して切る。

衝動 →（Cursor 調査で技術的事実を確定）→ 冷静な戦略判断、という流れがうまく回った日。

### 5. Treasury wallet (...0099) の調査

faucet の source 候補として treasury を検討したが、調査の結論:

- `...0099` は **vanity address**（env `TET_TREASURY_ADDRESS` で渡した固定 hex）。
- 対応する **mnemonic / 秘密鍵は存在しない**。
- `wallet_id = Ed25519 公開鍵 hex` であり、署名 transfer には秘密鍵が要る。treasury は鍵がないので **署名経由の transfer 不可**。専用の特権引き出し API も無い（`withdraw_treasury_to_founder` は別 wallet `dex:treasury` 用）。
- → faucet の source には使えない。

### 6. Faucet 設計確定 — **既存実装の発見**

一から作ろうとしていたが、調査したら **既に実装済み**だった。

- エンドポイント: `POST /ledger/faucet`、`POST /faucet`（dev alias）。
- **Source: worker pool (`...0001`)** — genesis で 50% (5B TET) が配分されている system wallet。
- **Auth: admin Bearer token**。
- **署名不要** — 特権 ledger メソッド `admin_rest_faucet` が worker pool → 宛先 wallet へ直接移動。1 wallet 1 回 + per-IP rate limit 付き。

### 7. Admin token 生成と enable

- `openssl rand -hex 32` で 64 文字の token を生成。
- 一度「これ漏れたらまずいやつだ」と気づいて作り直し（founder としての security 本能が正しく働いた）。
- `/root/admin_token.txt`（`chmod 600`）に保存。
- systemd service file に `Environment="TET_ADMIN_API_KEY=..."` を追加。
- `nano` 編集で typo を 3 回やったが、毎回 verify する習慣で発見・修正。
- `daemon-reload` + `restart` 成功。

### 8. Faucet production test

| Test | 操作 | 結果 |
|------|------|------|
| 1 | 正常 claim | **100 TET credit**、`audit_hash` 記録 |
| 2 | 同一 IP で再 claim | **IP rate limit 発動**（期待通り） |
| 3 | 認証なし | **UNAUTHORIZED reject**（期待通り） |

3 ケースすべてが期待通りで、faucet が production-grade に振る舞うことを確認。

## Lessons (教訓)

- **既存コードを理解することが効率の核**。faucet を一から作らずに済んだのは、「まず調べる」をやったから。書く前に読む。
- **Cursor 調査 → 実装 の order が重複作業を防ぐ**。先に実装に飛びついていたら、既にある faucet を二重に作っていた。
- **衝動を事実で冷やす**。「founder lock を外して世に出す」という衝動を、Cursor 調査（= 1 年クリフが既に焼き込み済み、という技術的事実）が止め、戦略 C という冷静な結論に着地させた。
- **verify 規律が typo を救う**。token の typo を 3 回とも発見・修正できたのは、編集後に必ず command で verify する習慣のおかげ。security に関わる設定ほど、この規律が効く。
