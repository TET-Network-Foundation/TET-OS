# 2026-05-28 (木) Sprint 4 Day 2 — Hardening + 初の cross-region P2P sync + multi-swarm bug fix

## Summary

VPS (Finland) を本番ノードとして hardening し、systemd で自動起動・ufw/fail2ban で防御・固定 port・永続 DB を整えた。その上で **初めて 2 ノードの cross-region P2P 接続**（スイス Mac ⇄ フィンランド VPS）を成立させ、CAAC のロール分化（VPS=PoR edge / Mac=PoC compute）を実地で確認した。

しかし VPS restart 後に sync が壊れた。症状を追うと **「3 つの libp2p swarm が全部同じ port 4001 を listen しようとして衝突する」** という設計上のバグに行き着いた。"片っ端から直す" のではなく、診断 → 設計 → 限定修正の規律で Option A（swarm ごとに別 port）を選び、commit `7a23ee6` で解消。最終的に **VPS height 3471 / Mac height 3471 / state_root 完全一致** という、誰にも見せられる形の cross-region block sync を達成した。

## Key Achievements

### 1. VPS hardening (Sprint 4 Day 2)

- **systemd**: `tet-core` を auto-start enable（再起動後も自動復帰）。
- **libp2p port 固定**: `TET_P2P_LISTEN=/ip4/0.0.0.0/tcp/4001`（以前は `tcp/0` でランダム → bootnode multiaddr が安定しなかった）。
- **ufw firewall**: `22 / 4001 / 5010` のみ open。それ以外は閉じる。
- **fail2ban**: 導入時点で既に **61 fails / 8 IP banned**。公開 IP は即座に殴られるという現実を数字で確認。
- **4GB swap**: VPS の小メモリで `cargo build` が OOM しないよう build resilience を確保。
- **永続 DB**: `/opt/tet-core-data` に移設（再デプロイで ledger が消えない）。

### 2. 初の cross-region P2P 接続 (CH ⇄ FI)

- VPS PeerId: `12D3KooWRSgxxdox2sePbfrZEgawDY1hbWCmQmXqnb6MggmXo6xf`
- **CAAC ロール実証**: VPS = PoR (edge)、Mac = PoC (compute)。同じバイナリが環境に応じて役割を自己決定する設計が、机上ではなく実ネットワークで動いた。
- **PING OK** → `chain_hello` 交換 → **state_root 一致** までを確認。
- VPS 側に mining 設定追加: `TET_AUTO_MINE=1`, `TET_BLOCK_TIME_SEC=5`。

### 3. multi-swarm port collision bug の発見と修正

VPS restart 後、sync が動かなくなった。

**症状**

- `[P2P] PING FAIL err=Ping protocol not supported`
- `[P2P-block] bootnode dead (no hello within timeout)`
- VPS 側: `GOSSIP PUBLISH ERROR topic=/tet/v1/blocks err=InsufficientPeers`

**根本原因**

tet-core は 1 プロセス内で 3 つの libp2p swarm を起動していた。そして **3 つとも同じ `TET_P2P_LISTEN`（4001）を listen しようとしていた**。

| Swarm | module | identify | 役割 |
|-------|--------|----------|------|
| block-plane | `p2p.rs` | `/tet/identify/1.0.0` | **block sync 本体**（ping + chain-sync + block-sync） |
| nexus | `p2p_network.rs` | `/nexus/1.0.0` | inference gossip + relay + WebRTC |
| ledger | `network.rs` | (なし) | ledger gossip |

同一 TCP port は 1 つの swarm しか bind できないため、OS が 2 つ目以降を拒否。**どの swarm が 4001 を勝ち取るかは非決定的**で、block-plane 以外が取ると chain-sync プロトコルが存在せず、dial してきた peer は "Ping protocol not supported" → "bootnode dead" 判定に落ちる。restart で順序が変わって表面化した、典型的な競合バグだった。

**診断 → 設計 → 限定修正**

- 診断: Cursor に「**修正禁止・調査のみ**」で 3 swarm 構成を洗い出させ、listen / identify / protocol / bootnode dial の担当を確定。
- 設計: 修正方針を Option A〜D で評価し、**Option A（swarm ごとに別 port）** を採用。理由は block-plane を 4001 のまま維持すれば、既存 bootnode multiaddr (`.../tcp/4001/p2p/...`) と `TET_BOOTNODES` がそのまま有効で、sync が確実に block-plane 経由になるから。
  - block-plane: `TET_P2P_LISTEN`（default 4001、据え置き）
  - nexus: `TET_NEXUS_P2P_LISTEN`（**新規**、default 4003）
  - ledger: `TET_LEDGER_P2P_LISTEN`（**新規**、default 4005）
- 実装: Cursor を **限定 scope** で使い、`main.rs` / `p2p_network.rs` / `network.rs` の listen 設定のみ変更。protocol / behaviour / topic は一切触らない。加えて **silent fail 防止の bind log** を全 swarm に追加（成功は `bound listen=...`、失敗は ERROR）。

**Commit**: `7a23ee6` — `fix: separate libp2p swarm listen ports`

**検証**: VPS incremental rebuild **1m04s** → restart → `ss` で `0.0.0.0:4001 / 4003 / 4005 / 5010` がそれぞれ別 bind されていることを確認。

### 4. 完全 block sync の実証

- Mac を rebuild → clean DB で再起動。
- **PING OK, rtt 55ms**（以前は FAIL）。
- sync engine の高度機能が動作: `STATE SYNC DETECTED`、`BACKFILLED BRANCH REORG APPLIED` など。
- 最終結果: **VPS height 3471 / Mac height 3471 / state_root 完全一致 (`0x5a7aa8d9db0a...`)**。

## Lessons (教訓)

- **"片っ端から直す" を避けた**。診断（調査のみ）→ 設計（Option 比較）→ 限定修正、という順序を守ったことで、3 swarm の絡んだ問題を最小差分で閉じられた。焦って複数箇所を同時にいじっていたら、原因と無関係な変更でさらに沼っていた。
- **silent fail がバグを隠していた**。起動時の `listen_on` 失敗を ERROR として出していなかったため、「2 つ目以降の swarm が port を取れていない」ことがログから見えなかった。→ 今後 **すべての `listen_on` は成功/失敗を明示 log する**（今回その規律を実装に焼き込んだ）。
- **Cursor は scope を厳格に切れば暴走しない**。「調査のみ・修正禁止」「この 3 ファイルの listen 設定だけ」と prompt を絞ると、余計なリファクタをせず、信頼できる差分を出す。
